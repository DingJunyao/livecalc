# BUGFIX：移动端价格记录单位下拉 + 单位编辑体验（量/单位、继承原料）

> 2026-10-14。用户实机反馈六条：①自定义单位在价格记录页下拉里「仍然看不到」；
> ②改商品名后价格记录页要手动刷新才更新；③单位/密度编辑是对话框，希望像价格记录编辑那样是整页；
> ④换算系数多余（DB 都填 1）；⑤「量」「单位」两个框高度不等、名称该叫「量」「单位」、
> 界面上那个「单重」多余；⑥商品自定义单位时单位下拉看不到其所属原料的自定义单位（应继承）。

## ① 价格下拉「看不到自定义单位」的真因（有数据佐证）

逐层回放（真实开发库 + 运行中的后端 + 铸 JWT 以 App 视角调接口）：

| 层 | 结论 |
|---|---|
| 接口 | `GET /entities/{type}/{id}/units` 正常返回（含 `unit_name`、已过滤 `is_active`；库里 279 活跃 / 0 停用 / 0 空名） |
| 原料回退 | 239/239 依赖原料级覆盖的活跃商品都能解析到 `ingredient_id` 并取到原料覆盖（管理员与非管理员一致）；`GET /products/entity/{id}` 缺 `X-Timezone` 会 400，App 有全局注入（`auth_interceptor.dart:18`），所以 App 内这一跳是通的 |
| **前端基准列表** | **真因**：移动端把「全局单位基准」写死成 12 项常量（`g,100g,kg,斤,个,ml,L,盒,袋,瓶,罐,包`），web 是现拉 `/units/`（54 项）。把 767 条真实 (商品, 单位) 组合全量回放：49 条用了常量外的单位，**其中 42 条移动端缺失、web 有** |

42 条里最典型的是：`把`（小葱/香菜/油麦菜/芹菜/苋菜/韭菜…）、`条`（黄花鱼/大黄鱼/小白鲳）、
`块`（浓汤宝）、`颗`（西葫芦/青茄子/水果玉米），以及 **`mL`**——常量写的是小写 `ml`，
于是用 `mL` 记下的记录（香油 ×10、香醋 ×9、牛奶 ×3）在移动端**根本选不回来**。
用户说的「自定义单位」也可能指单位管理里新增的全局单位（例如 `桶`，常量里没有）。

修复：新增 `loadGlobalUnitNames()`（`GET /units/?limit=200`，失败返回空 → 回退旧常量），
新增页与编辑页都改用它作基准；行解析放宽为 `unit_name ?? name`、跳过显式停用行、
支持 `{items:[...]}` 包裹；请求失败改为 `dart:developer` 留痕——
原来 `catch (_) {}` 会把「关联原料那一跳」的所有单位静默吞掉，出问题时毫无线索。

## ② 改名后价格列表自动更新

后端改名已同步 `product_records.product_name`（见上一条要点），剩下的是客户端缓存：
商品编辑保存成功且名字确实变了时，保存前调用 `priceListProvider.notifier.loadRecords()`
（mounted 守卫 + 失败留痕），新建模式不刷。web 端 `PricesView` 每次进入都 `onMounted` 重拉
且无 keep-alive，不需要改。

## ③ 单位/密度编辑改回整页

移动端 `EntityUnitsCard` 仍内联展示列表（区块右上「添加」、行内编辑/删除、待审行只读），
点添加/编辑改为 push 整页（覆盖底部导航，编辑时不误触），保存按钮遵循全局
「保存按钮位置」本地设置（右上角 / 页面下方）。对话框只在删除确认等场景保留。

## ④⑤ 换算系数移除与「量 / 单位」

- 表单不再有换算系数，保存固定发 `conversion_factor: 1`（web 与移动端一致）。
- **老数据不丢**：打开编辑时把「系数 × 量」合并进「量」预填（`12 + 空量 → 量 = 12`），
  因此把系数固定为 1 不会把重量改小；列表展示对历史非 1 系数仍按原值乘算。
- 标签改「量」「单位」（三语）；两控件等高（都按数值框的 56 高度基准，单位框给同样的
  contentPadding；web 端统一 `variant=outlined + density=comfortable + persistent-hint`，
  之前不等高是 Vuetify 两个控件默认 density 不同：48px vs 56px）。
- 单位下拉的默认项不再显示「单重（g/个） · 默认 (g)」这类文案，只显示「默认（克）」。

## ⑥ 继承关联原料的自定义单位

- 后端：`resolve_override_amount` 新增 `_find_referenced_override`，允许引用「同实体」或
  「商品 → 其关联原料」的覆盖；其余（他人实体/无关原料）仍按悬空处理（不臆估）。
  提议执行器校验同步放宽，文案改为「只能引用同一实体（{type}/{id}）或其关联原料的自定义单位」。
- 两端 UI：商品的单位下拉合并「本商品 + 关联原料」两条来源，同名/同 id 时本商品覆盖胜出，
  继承项标注「继承自原料」；**防环守卫与链解析都在合并表上走**（visited + 深度 8），
  因此 `1箱 = 12 盒` 在「盒」定义于原料时也能正确显示与保存。
- 快速填写每行的单位菜单也并入该行商品的自定义单位（按 productId 缓存、并发上限 4、
  失败回退原常量）。

## 经验

1. 「下拉里选不到某个单位」先分清是**实体自定义单位**还是**全局单位**：两端基准列表口径不一致
   （一端硬编码、一端现拉）时会表现成同一种症状，而且硬编码那端还会因为大小写
   （`ml` vs `mL`）永远选不回自己刚存的记录。基准列表必须与数据源同源。
2. 静默 `catch (_)` 是这类问题的最大障碍：一个跳跃（原料回退）失败就静默删掉整类单位，
   日志里什么都没有。改成「只吞请求异常 + 留痕」后，下一次线上复现能直接看日志定位。
3. 去掉一个界面字段前先问「这个字段承载的信息会不会丢」：换算系数被移除后，
   老数据的 `系数 × 量` 必须在打开时折算进「量」，否则一次编辑就把语义改小。
4. 继承（子实体用父实体的定义）要三处同时支持：**解析**（换算链）、**校验**（写入口）、
   **防环**（客户端下拉 + 服务端环检测），少一处就表现为「能选但保存失败」或「保存了但算错」。
