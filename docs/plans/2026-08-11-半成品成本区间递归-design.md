# 半成品成本区间递归（修复 avg 超出 min/max 区间）

## 背景与根因

菜谱「成本趋势」图表出现平均值超出区间的不可能结果（蛋炒饭 avg=15.80，区间 6.14~13.24）。

根因在提交 `cc55a18`（重构菜谱成本区间趋势计算逻辑）引入的**口径撕裂**：`calculate_recipe_cost_range_trend` 里 avg 和 min/max 走两条独立路径——

- **avg_cost**：直接调用 `calculate_recipe_cost_as_of`，包含完整的 5 层价格源降级链（直接商品加权 → ingredient fallback → 按名称匹配 → 半成品菜谱推导 → contains 子食材聚合）。
- **min/max_cost**：函数内手写一套，只覆盖「直接商品 + fallback 链 + substitutable + CONTAINS 子食材」，**缺少「按名称匹配」和「半成品菜谱推导」两条路径**。

后果：任何只在「半成品推导」或「名称匹配」下才有价格的食材，在 min/max 路径贡献 0，在 avg 路径却算出了正成本，把 avg 顶到 max 之上。

蛋炒饭的元凶是**米饭**（ing 179）：直接商品零价格记录、无 fallback、无 contains，但是半成品（`serving_weight=400`，由菜谱 185「电饭煲蒸米饭」产出）。avg 通过 `_get_cost_from_recipe` 推导出 3.66 元，min/max 完全漏算。

## 目标

让 min/max/avg 三者基于**同一组价格源**计算，保证数学上 `min ≤ avg ≤ max` 恒成立，且半成品的价格波动也能通过递归传导进区间。

## 方案设计

### 整体架构：双轨收敛为单轨

新增递归函数：

```python
def calculate_recipe_cost_range_as_of(
    recipe_id, user_id, as_of_date, db, visited=None, tz="UTC"
) -> dict | None:
    """返回 {min_cost, max_cost, avg_cost, cost_breakdown}"""
```

每个食材按其价格来源产出一组 `(min, max, avg)`，菜谱总成本三档各自求和。由于对每个食材 `min_i ≤ avg_i ≤ max_i`，求和后总体 `min ≤ avg ≤ max` 恒成立。

`calculate_recipe_cost_range_trend` 的逐天循环里，删掉现有的 avg 双轨（[recipe_service.py:1397](backend/app/services/recipe_service.py#L1397)）和手写 min/max（[recipe_service.py:1422](backend/app/services/recipe_service.py#L1422)），改成每天只调一次新函数。

### 各价格来源的极值规则

统一原则：**min/max 基于当天记录的单价极值，avg 保持现状口径不变**。所有单价归算到「元/克」（沿用 `_convert_record_to_price_per_gram`），用量统一走 `_get_effective_quantity`。

| 价格来源 | min_cost | max_cost | avg_cost（与现状一致）|
|---|---|---|---|
| direct 直接商品 | 当天最便宜记录单价 × 用量 | 当天最贵记录单价 × 用量 | 加权均价 × 用量（`resolve_direct_weighted_for_cost`）|
| fallback / 名称匹配 | 回退（或匹配）食材当天记录极值 × 用量 | 同左 | 现状那条记录单价 × 用量 |
| recipe 半成品 | 递归制作菜谱 min ÷ 产量 × 用量 | 递归 max ÷ 产量 × 用量 | 递归 avg ÷ 产量 × 用量（= 现状 `_get_cost_from_recipe`）|
| contains 聚合 | 子食材 min_ppg 按 strength 加权 × 用量 | 子食材 max_ppg 加权 × 用量 | 现状加权 avg_ppg × 用量 |

半成品递归：`_get_cost_from_recipe` 出 range 版本，复用现有循环检测（`visited`）和份重桥接（`servings × serving_weight`）骨架，把「调 `calculate_recipe_cost_as_of` 拿单点」改成「调 `calculate_recipe_cost_range_as_of` 拿三元组」，再 `÷ total_yield_g` 转每克三档单价。

### 降级链一致性（修复核心）

range 函数内部按**统一优先级**找来源：direct → fallback → 名称匹配 → 半成品递归 → contains 聚合。命中的第一个有效来源**同时**产出三档。绝不允许 avg 取 direct、min/max 取 fallback 这种错位——这正是原 bug 的根源。

### 错误处理铁律：三档同生共死

某食材所有来源都无价（含脏数据过滤后池空）→ 三档都贡献 0 并跳过。半成品递归返回 None / 循环命中 / contains 子食材全空 → 整组跳过。绝不能 min/max 算了 avg 漏算。

## 关键决策

1. **用量口径**：`_get_effective_quantity` 现状对 quantity_range 取 **max**（非中值，注释「取平均值」失实）。range 版本统一沿用，三档用量一致。quantity_range 当前无「推荐值」字段，全程沿用现状。
2. **脏数据过滤（取舍 B）**：极值计算过滤 `price ≤ 0` 或 `standard_quantity ≤ 0` 的记录（防 min=0，如大米 min_unit=0），不动数据本身。
3. **性能策略（取舍 C）**：先正确后优化。逐天递归调 range 函数，月度 30 天先跑通；批量预加载优化留作后续（YAGNI）。

## API / 前端影响

`/recipes/{id}/cost-history-range` 响应字段（`min_cost/max_cost/avg_cost/breakdown`）不变，**前端零改动**。breakdown 顺带补 `cost_source` 字段（向后兼容，便于将来 tooltip 展示来源）。

## 测试计划（TDD，蛋炒饭 280 做端到端夹具）

1. **核心回归**：每个返回日期断言 `min ≤ avg ≤ max`。
2. **半成品递归**：米饭三档都 > 0，且 min/max 来自大米 8 商家极值。
3. **脏数据过滤**：`price ≤ 0` 记录不进极值。
4. **循环检测**：A→B→A 套娃不死循环、返回 None。
5. **降级一致**：构造 direct 无价的食材，断言三档落到同一 fallback 来源。

## 性能备注

当前 `calculate_recipe_cost_as_of` 是逐食材查库（非批量），range 版本同样。月度趋势 30 天 × 递归（半成品嵌套）会比现在慢。cc55a18 之前的批量预加载思路可借回优化，属第二阶段，本次不展开。
