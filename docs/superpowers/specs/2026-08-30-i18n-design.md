# 本地化与 RTL 支持设计

## 背景

Livecalc 目前以中文文案为主，Web 前端、后端和移动端都存在硬编码界面文本。日期、时间、数字和金额展示缺少统一的区域格式层，也没有界面文字方向支持。随着用户范围扩大，需要同时支持多语言、多区域格式和阿拉伯语 RTL。

现有约束：

- Web 没有接入 i18n 框架，静态文案分散在模板和脚本中。
- Flutter 已依赖 `flutter_localizations` 和 `intl`，但 `MaterialApp` 当前固定中文。
- 后端大量用户可见 `detail` / `message`、校验错误、邮件和内置数据名称直接返回中文。
- 数据库已有 `X-Timezone` 口径和现有币种模型，本地化不能破坏这些契约。

## 目标

- 支持 `zh-CN`、`en-US`、`ar` 三种界面语言，其中 `ar` 完整支持 RTL。
- 支持独立的区域格式选项，用于日期时间、数字、百分比和金额展示。
- 登录用户的服务端偏好持久化；未登录 Web 用户使用本地存储；未登录移动端跟随系统语言。
- 后端用户可见错误、邮件和内置目录名称按目标用户语言输出。
- 保持现有 API 数据契约不变：日期仍为 ISO 字符串，数字仍为 decimal，币种仍为 ISO code 加数值。

## 非目标

- 不自动翻译用户和业务数据，例如商品名、原料名、菜谱步骤、商户名称和用户备注。
- 不把 `format_locale` 绑定到币种选择；币种继续使用现有用户币种 / 地区模型。
- 不重写表单输入解析，编辑值仍使用现有点号小数和现有日期输入口径。
- 不引入跨 Web、Flutter 和后端的共享翻译生成器。
- 不翻译日志、堆栈和内部异常。

## 分支策略

1. `feat/i18n` 从 `master` 创建，只包含 Web 前端、前端本地模式和后端改动。
2. `feat/i18n` 验证通过并形成可交付提交。
3. `feat/i18n-mobile` 从 `feat/mobile-app` 创建。
4. 将 `feat/i18n` 合并到 `feat/i18n-mobile`。
5. 只在 `feat/i18n-mobile` 上处理 Flutter 和移动端专属问题。

若实施前远端 `master` 或 `feat/mobile-app` 更新，先同步对应基础分支，再继续上述顺序。

## 语言与格式模型

### 界面语言

界面语言只允许：

- `zh-CN`
- `en-US`
- `ar`

`locale` 决定：

- 界面文案。
- 文字方向：`zh-CN` 和 `en-US` 为 LTR，`ar` 为 RTL。
- 默认后端文案语言。
- 默认区域格式。

不支持的语言按 `zh-CN` 回退。

### 区域格式

`format_locale` 是独立偏好，允许：

- `null`：跟随 `locale`。
- `zh-CN`
- `zh-TW`
- `en-US`
- `en-GB`
- `ja-JP`
- `de-DE`
- `id-ID`
- `ar-EG`

`format_locale` 只影响展示格式，不影响翻译、文字方向、币种和数据存储。

### 用户偏好

登录用户：

- `users.locale` 保存界面语言。
- `users.format_locale` 保存区域格式，可为空。
- 两者暴露到用户响应和个人资料更新 API。
- 保存时按上述白名单校验。

未登录 Web：

- 使用 localStorage 保存 `locale` 和 `format_locale`。
- 有效期和清理规则跟随现有本地模式设置。

未登录移动端：

- 界面语言按系统 locale 匹配支持列表。
- 区域格式默认跟随匹配后的界面语言。
- 登录后使用服务端偏好覆盖本地推断值。

## 请求与非请求上下文

### 请求上下文

Web 和移动端请求统一通过标准 `Accept-Language` 发送有效界面语言；`format_locale` 不通过该 Header 发送，只作为用户偏好由后端读取和返回。

后端解析顺序：

1. 当前登录用户存储的 `locale`。
2. `Accept-Language` 中第一个受支持语言。
3. `zh-CN`。

后端返回给前端的用户对象始终携带 `locale` 和 `format_locale`，避免请求头和用户偏好不一致时前端状态漂移。

### 非请求上下文

邮件、后台通知和其他异步任务使用目标用户或收件人的存储 `locale`。收件人没有偏好时使用 `zh-CN`。

同一批通知存在多个收件语言时，按语言分组生成和发送。

## Web 架构

- 引入 `vue-i18n`。
- 翻译资源放在 `frontend/src/locales/{zh-CN,en-US,ar}.json`。
- 建立 locale store，统一管理：
  - 界面语言。
  - 区域格式。
  - 登录用户偏好同步。
  - 未登录 localStorage 读写。
  - 系统语言初始化。
- Vuetify locale 与应用 locale 同步。
- `ar` 同步 Vuetify RTL 配置。
- 更新 `document.documentElement.lang`；`ar` 时设置 `dir="rtl"`，其他语言设置 `dir="ltr"`。
- 模板静态文案替换为 `$t()`，脚本内通过共享 `t()` 使用同一翻译资源。
- 翻译 key 按页面 / 组件 / 领域组织，避免单个超大的平铺文件难以审阅。

### RTL

- 布局优先使用逻辑属性和现有组件 RTL 能力。
- 审计现有 `margin-left`、`margin-right`、`left`、`right`、`text-align` 等物理方向样式，仅改造成有真实 RTL 问题的位置。
- 图表、地图坐标轴和地理位置图层保持 LTR 数据方向，不翻转经纬度或时间轴数值方向。
- 阿拉伯语界面中的数字、日期编辑值保持 LTR 书写顺序，展示文本仍按 RTL 排版。

## 格式化层

Web 增加一个集中格式化模块，基于浏览器原生 `Intl`：

- 日期：`Intl.DateTimeFormat`。
- 时间：`Intl.DateTimeFormat`。
- 数字：`Intl.NumberFormat`。
- 百分比：`Intl.NumberFormat` 的 percent 格式。
- 金额：按 `format_locale` 格式化数值，并显示 ISO 币种 code。

格式化模块只负责展示。API 输入输出、数据库存储和计算逻辑继续使用 ISO 字符串、decimal 数值和 ISO 币种 code。

表单初始值和提交值不做区域格式反解析。用户看到和提交的编辑值仍使用现有输入规则，以避免逗号小数、阿拉伯数字形状和 locale 日期顺序引入解析歧义。

## 后端架构

- 使用 Python 标准库 `gettext`。
- 中文源文案作为 msgid 和默认 fallback。
- 为 `en_US` 和 `ar` 维护 PO/MO 资源。
- 包装用户可见错误输出：
  - API `detail` / `message`。
  - Pydantic / FastAPI 校验错误。
  - 默认邮件文案。
  - 内置目录展示名。
- 保持内部异常、日志和调试信息原文，不做翻译。

邮件模板选择按收件人 locale 执行，缺失时回退 `zh-CN`。

## 数据模型与迁移

### 用户偏好

`users` 新增：

- `locale`：可空。存量用户迁移为 NULL；NULL 表示按请求语言解析，最终回退 `zh-CN`。用户主动保存后写入受支持语言。
- `format_locale`：可空。

存量 NULL 不视为无效。用户资料更新提交非空值时，两个字段分别使用界面语言和区域格式白名单校验。

### 邮件模板

`email_templates` 新增：

- `locale`，默认 `zh-CN`。

调整唯一约束：

- 旧约束：`key`。
- 新约束：`key + locale`。

迁移时：

1. 现有模板行补 `zh-CN`。
2. 创建新的联合唯一约束。
3. 种子补充 `en-US` 和 `ar` 模板。

后台邮件模板列表按语言分组展示；发送时优先取收件人语言，再回退 `zh-CN`。

### 迁移交付

除 Alembic migration 外，按项目约束同时提供 SQLite、MySQL、PostgreSQL SQL 脚本；PostGIS 版本仅在与 PostGIS 相关时提供。现有部署优先执行 SQL 脚本，新环境按现有初始化流程执行。

## 内置目录

不为目录行增加多语言数据库字段。原始 `name` 继续保存用户可见的业务值，接口额外返回 locale-aware `display_name`。

### 币种

- 管理员可编辑的数据库 `name` 保持不变。
- 内置 ISO 币种返回按 locale 计算的 `display_name`。
- 自定义或管理员重命名后的币种优先沿用数据库 `name`，当实现能明确识别内置 ISO code 且管理员未重命名时使用 locale 名称。
- 币种选择仍由现有用户币种 / 地区模型决定。

### 地区

- 国家和地区返回 locale-aware `display_name`，优先使用平台 / CLDR 名称。
- 中国行政区划没有权威本地化数据时，回退顺序为 `name_en -> name`。
- 现有 `name` 字段和存储数据不变。

### 单位、营养素和原料分类

- 通过稳定 code / key 建立前端或后端展示表。
- 内置项返回或渲染 `display_name`。
- 用户创建项保留原文。

### USDA 数据

- `en-US` 直接展示来源英文描述。
- `zh-CN` 和 `ar` 优先使用已有翻译。
- 无翻译时回退英文，不生成机器翻译。

## Web 本地模式

本地模式复用 Web locale store、翻译资源和格式化模块。

本地 API 错误返回稳定错误 code 或 i18n key，由前端翻译；不在浏览器实现 gettext。远端模式和本地模式应尽量呈现同一错误文案。

本地模式内置目录的 `display_name` 与远端接口保持同一规则，无法取得平台名称时回退现有名称。

## Flutter 与移动端

移动端阶段只在 `feat/i18n-mobile` 实施：

- 使用官方 `flutter gen-l10n` 和 ARB 文件。
- `MaterialApp.locale` 使用服务端用户偏好、本地存储或系统语言。
- Dio 统一发送 `Accept-Language`。
- 集成 `flutter_localizations` 和 `intl` 的日期、数字、百分比格式化。
- 阿拉伯语通过 Flutter RTL 机制生效。
- 审计移动端方向性布局、图标、抽屉、返回行为和列表尾部操作。
- 图表和地图坐标保持 LTR。
- 移动端表单编辑值与 Web 一致，不做区域格式反解析。

Web 端通用文案和格式化改动来自 `feat/i18n` 合并，移动分支只补移动端专属接入和布局问题。

## 验证

### Web

- 翻译 key 完整性检查：三种界面语言 key 集合一致。
- 执行 `cd frontend && npm run build`。
- 浏览器检查 `zh-CN`、`en-US`、`ar` 的桌面和移动宽度。
- 阿拉伯语确认 `dir="rtl"`、Vuetify RTL、导航、表格、表单、对话框和抽屉方向正确。

### 格式化

为代表性 locale 增加最小检查：

- `en-US`
- `en-GB`
- `de-DE`
- `ja-JP`
- `ar-EG`

覆盖日期、时间、数字、百分比和金额展示。

### 后端

使用 pytest 覆盖：

- `Accept-Language` 解析和回退。
- 用户 `locale` / `format_locale` 读取与更新校验。
- 用户可见错误翻译。
- 邮件模板按收件语言选择和回退。
- 内置目录 `display_name` 回退。
- 数据库迁移 smoke test 或等效最小验证。

### 移动端

- 执行 `cd mobile && flutter gen-l10n`。
- 执行 `cd mobile && flutter analyze`。
- 执行 `cd mobile && flutter test`。
- 阿拉伯语真机或模拟器 RTL smoke test。

## 交付顺序

1. 后端 locale 基础设施、用户偏好和迁移。
2. Web i18n 基础设施和设置入口。
3. Web 静态文案、目录 `display_name` 和本地模式错误文案替换。
4. Web 展示格式层和 RTL 修复。
5. `feat/i18n` 后端、前端和格式化验证。
6. 创建 / 更新 `feat/i18n-mobile` 并合并 `feat/i18n`。
7. Flutter l10n、请求头、用户偏好同步和移动端 RTL 修复。
8. 移动端验证和人工 RTL 验收。
