# Web And Backend i18n Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver locale preferences, localized backend responses, Web formatting, static UI translation, local-mode errors, and Arabic RTL on `feat/i18n`.

**Architecture:** Backend resolves one effective UI locale per request, persists user preferences, and keeps API storage contracts unchanged. Web owns translation and display formatting through `vue-i18n` plus native `Intl`, with a separate nullable format locale. Mobile work is excluded and will be planned only after this branch is merged into `feat/i18n-mobile`.

**Tech Stack:** FastAPI, SQLAlchemy, Alembic, Python `gettext`, Babel CLDR data, Vue 3, Pinia, Vuetify, `vue-i18n`, native `Intl`.

**Spec:** `docs/superpowers/specs/2026-08-30-i18n-design.md`

## Global Constraints

- UI locales are exactly `zh-CN`, `en-US`, and `ar`; unsupported values fall back to `zh-CN`.
- Format locales are exactly `null`, `zh-CN`, `zh-TW`, `en-US`, `en-GB`, `ja-JP`, `de-DE`, `id-ID`, and `ar-EG`.
- `locale` controls text and direction; `format_locale` controls display formatting only.
- Currency selection remains the existing user currency / region model.
- API dates remain ISO strings, numbers remain decimal values, and currency remains ISO code plus numeric amount.
- Do not rewrite form input parsing for locale decimal separators or date orders.
- Logs, stack traces, and internal exceptions remain untranslated.
- Preserve the existing `X-Timezone` header.
- Charts, maps, and geographic coordinates remain LTR.
- Database changes require Alembic plus SQLite, MySQL, and PostgreSQL SQL scripts; no PostGIS script is needed.
- Tasks 1 through 14 each end with their listed verification and a conventional commit; Task 15 commits only if its plan edit is needed.

## File Structure

- `backend/app/core/i18n.py`: locale parsing, fallback, gettext loading, and translation helpers.
- `backend/app/locales/`: gettext PO/MO catalogs for `en_US` and `ar`.
- `backend/app/services/catalog_display.py`: CLDR-backed currency and region display names.
- `backend/scripts/check_i18n_messages.py`: AST check that backend user-visible messages have catalogs and no dynamic Chinese detail strings.
- `frontend/src/locales/`: one JSON message catalog per UI locale.
- `frontend/src/plugins/i18n.ts`: composition-mode `vue-i18n` instance and shared script translator.
- `frontend/src/stores/locale.ts`: locale state, persistence, user synchronization, DOM direction, and Vuetify synchronization.
- `frontend/src/utils/format.ts`: locale-aware date, time, number, percent, and money formatting.
- `frontend/src/utils/localErrors.ts`: stable local-mode error codes mapped to frontend translations.
- `frontend/scripts/check-i18n.mjs`: locale-key completeness and Han-text source check.

```python
from babel.numbers import get_currency_name
from babel import Locale
from app.services.currency_seed import CURRENCIES, CURRENCY_NAMES


_BABEL_LOCALES = {"zh-CN": "zh_CN", "en-US": "en_US", "ar": "ar"}


def currency_display_name(code, stored_name, locale):
    default_name = CURRENCY_NAMES.get(code, CURRENCIES.get(code, {}).get("name", code))
    if stored_name and stored_name not in (code, default_name):
        return stored_name
    try:
        return get_currency_name(code, locale=_BABEL_LOCALES[locale])
    except Exception:
        return stored_name or code


def region_display_name(region, locale):
    if region.level == 0 and region.iso_country:
        try:
            return Locale(_BABEL_LOCALES[locale]).territories.get(
                region.iso_country, region.name
            )
        except Exception:
            return region.name
    if locale.startswith("zh"):
        return region.name
    return region.name_en or region.name
```

- [ ] **Step 2: Convert local handlers**

Define:

```ts
export function localError(
  code: string,
  status = 400,
  params: Record<string, unknown> = {},
) {
  return { status, code, params }
}

export function translateLocalError(error: unknown): unknown {
  if (typeof error !== 'object' || error === null || !('code' in error)) return error
  const localError = error as { status?: number; code: string; params?: Record<string, unknown> }
  return {
    status: localError.status ?? 400,
    message: t(`localErrors.${localError.code}`, localError.params ?? {}),
  }
}
```

Wrap all `localGet`, `localPost`, `localPut`, and `localDelete` catches with `translateLocalError`. It maps `{ code, params }` to `t(\`localErrors.${code}\`, params)` and preserves status. User data may appear in params, never in the key.
